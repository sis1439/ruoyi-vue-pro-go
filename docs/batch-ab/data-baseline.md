## Representation decisions

- The PostgreSQL driver is gorm.io/driver/postgres v1.6.0 with pgx/v5 v5.6.0, GORM v1.31.1. Existing MySQL configuration remains a compatibility fallback; PostgreSQL acceptance uses database.driver=postgres and RUOYI_DATABASE_DSN.
- `BitBool` preserves its original integer Valuer and 0/1 meaning in PostgreSQL smallint, with CHECK IN(0,1). GORM default:0 on bool-kind fields bypasses the Valuer and binds bare false, which pgx cannot encode as int2. SQL-expression defaults `(0)`/`(1)` avoid that conversion and use database defaults with RETURNING. Audited bool update call sites explicitly bind BitBool (file master, comments, browse history, trade payment status, DIY/kefu/brokerage); native bool fields are untouched. Explicit true, default false/true, zero updates, query filtering and logical deletion are exercised on actual models. Native bool fields remain PostgreSQL boolean.
- ListFromCSV values retain text/varchar and their Scanner/Valuer behavior. JSON serializer fields retain json; GORM datatypes that explicitly select PostgreSQL JSONB retain jsonb. Go maps are not blanket-converted. Tests exercise SKU JSON properties, payment client JSON, CSV integer lists, timestamp offsets, time-of-day strings, and NULL dates.
- GORM maps native Go int on this 64-bit target to bigint unless a source tag specifies another type. Amounts stay integer fen, including aggregate results. The actual SKU/statistics tests preserve 3,000,000,001 fen without float conversion. Existing int32 model fields retain their source bounds; rates/percentages, weights and volumes remain their declared non-monetary types. This does not claim every service arithmetic path is overflow-safe.
- MySQL tinyint, int(11), longtext tags are normalized to PostgreSQL smallint, integer and text during DDL generation. The original tags remain traceable; production schema evolution uses explicit SQL, not runtime AutoMigrate.
- Source NOT NULL is retained. API required tags do not add constraints. Source nullable fields remain nullable; in particular source tenant_id defaults remain 0, while the separate TenantPlugin requires a trusted positive tenant for application writes. Direct SQL and migration credentials are privileged and not protected by that plugin.

## Constraints and indexes

Migration 2 adds tenant/live username and nonempty member mobile keys, role code and role assignment keys, singleton member/trade configuration, app key, and daily SPU statistics keys. Soft-deleted ordinary identifiers may be re-created. Query indexes target tenant/user order pages, order-item loading, SKU lookup, cart and coupon selection, tenant file listing, and product statistics source scans. Primary keys are from models. No foreign key was guessed from an xxx_id suffix.

Migration 5 retains nonempty external transaction identities even after soft deletion: trade tenant/no, pay tenant/app/merchant_order_id, refund tenant/app/merchant_refund_id, and payment extension tenant/no. Sources are CreateOrder idempotency lookup, validatePayRefundExist and notification lookup. This prevents a deleted row from permitting reuse of an external identifier. Empty historical/fixture identifiers remain outside these partial unique indexes. Existing deployments must inspect duplicates and reconcile deliberately before applying; migration fails rather than silently deleting data.

The manifest records exact reviewed index definitions. Remaining candidate uniqueness (cart merge policies, channel configuration replacement, notification task retries) needs the relevant service semantics and is intentionally not invented.

## Seeds and operational prerequisites

Tenant 1 uses PackageID=0, the explicit built-in system-tenant sentinel in TenantService.isSystemTenant and its menu-filter logic; no phantom package row is fabricated. Migration 3 seeds tenant 1, tenant_admin role, the Go routers' 175 non-IoT permission strings, explicit role/menu links, common_status dictionary, tenant member/trade configuration, the mall payment application and eight tenant-1 scheduler entries. Migration 6 adds the 38 newly enforced trade router permissions and their tenant-1 tenant_admin associations, without platform grants; order/config buttons attach to their existing pages and other buttons to Mall. Migration 4 adds six actual pages: product SPU, member user, trade order, files, trade configuration and member configuration; paths reference actual pinned admin src/views files. Other complete dictionary families, translations, optional menu pages and tenant provisioning workflows are not claimed complete. Seed permissions are source-backed; frontend visual/end-to-end acceptance belongs to the parent T01 work.

The bootstrap command separately creates a user with caller-supplied credentials and bcrypt, assigns tenant_admin, and optionally binds a validated bare hostname. It refuses to overwrite an existing administrator. The later security-agent request adds an explicit offline-only RUOYI_BOOTSTRAP_PLATFORM_ADMIN=true opt-in for a newly created user: it creates/assigns the reserved enabled system role platform_admin in addition to tenant_admin. No default or SQL seed grants that role; normal bootstrap remains tenant-only. Web role creation is separately guarded by the security agent. There is no default admin password or embedded merchant secret. It uses a silent SQL logger so a failing insert cannot print a password hash.

Trade/member defaults keep point deduction, brokerage, pickup and unconfigured promotional features off; refund reasons are minimal editable strings. No active coupon is fabricated. The mall pay app is disabled until merchant/channel credentials and callback URLs are configured; no pay channel, certificate or key is seeded. External service availability is not simulated as successful.

Core job seeds are enabled (status=1), scoped to tenant1, with actual source handler names and six-field cron. The parent owns tenant-aware scheduler registration and tests; these database seeds do not prove payment/refund job business correctness. File backend settings require local provisioning; no machine-specific storage path is seeded in immutable SQL.

## Data access audit and limits

Product statistics no longer execute IFNULL or unscoped Raw SQL. They require a trusted tenant, use model queries preserving soft-delete/tenant rules, replace a day's records transactionally, use COALESCE integer aggregation and a unique live daily key for retry protection. Paid-order IDs are bound in chunks of 1,000; the ID list is still materialized per tenant, so very large histories may require streaming. Concurrent duplicate daily runs can return a unique violation; they cannot persist two live rows. Transaction-agent changes replace member FIND_IN_SET with PostgreSQL string_to_array membership while retaining CSV storage.

`evidence/data-access-audit.txt` records remaining raw/table call sites. Optional IoT repositories still contain DATE_FORMAT/JSON_CONTAINS. Optional brokerage ranking uses table aliases/subqueries currently rejected by the security guard. The unconfigured member-mail path selects an email field absent from MemberUser; it is not part of first-phase required SMS/file/transaction behavior and remains an explicit unsupported path. These are not presented as PostgreSQL-compatible or silently disabled by this task. Parent T09/T10 owns the guard and the enabled-route scope.

Full database-column coverage is proven; full service-query, transaction, fault, frontend and external-channel correctness requires the other task evidence. No production readiness claim follows from this baseline.
